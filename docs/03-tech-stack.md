## 1. 하드웨어 제약

Oracle Cloud Always Free — Ampere A1 인스턴스.

| 항목 | 값 |
| --- | --- |
| CPU | 4 OCPU (ARM Ampere) |
| RAM | 24GB |
| 스토리지 | 200GB (**부트 볼륨 포함**) |

### 이 제약이 만드는 것

**ARM64다.** x86이 아니다. 도커 이미지는 arm64를 써야 하고, 네이티브 모듈이 있는 패키지는 arm64에서 설치해야 한다. 배포 방식(10장)이 이것 때문에 갈린다.

**VM이 하나다.** 앱도 DB도 한 머신에 있다. HA가 없고, 이 머신이 죽으면 서비스 전체가 죽는다. → 백업(11장)이 유일한 보험이다.

**Oracle 무료 계정 리스크가 있다.** 유휴 인스턴스 회수 정책이 있고, 계정이 정지되면 인스턴스와 데이터가 함께 사라진다. → **백업을 Oracle 밖에 둬야 하는 이유.**

### 디스크 구성

```
부트 볼륨   50GB   OS, 도커
데이터 볼륨 150GB  Postgres 데이터, 업로드
```

**분리하는 이유**: OS를 갈아엎거나 인스턴스를 재생성해도 데이터 볼륨은 떼었다 붙이면 그대로 살아남는다. 한 볼륨에 다 두면 OS 문제 하나에 전부 같이 간다.

## 2. 용량 분석 — 200GB로 충분한가

**충분하다.** 근거:

사용자 1명이 하루에 만드는 데이터
- DailyMission 약 5행
- DailyRecord 1행
- Reflection 1행

인덱스 포함 **약 1~1.5KB/일** → **약 0.5MB/년**

| 활성 사용자 | 1년 누적 |
| --- | --- |
| 1,000명 | 약 0.5GB |
| 10,000명 | 약 5~7GB |
| 100,000명 | 약 50GB |

텍스트와 숫자만 쌓이는 서비스다. DB가 디스크를 먹을 일이 없다.

### 실제로 200GB를 채우는 것들

DB가 아니라 이쪽이다. 전부 운영 습관 문제다.

- **도커 빌드 캐시 누적** ← 제일 흔함. 배포 스크립트에 `docker image prune` 필수
- **로그 방치** → 도커 로그 드라이버에 `max-size` / `max-file` 설정
- **Postgres WAL 미정리**
- **백업 파일을 같은 디스크에 쌓기** ← 백업을 외부로 보내면 애초에 발생 안 함
- **원본 이미지 업로드** → R2로 분리(12장)

### RAM

24GB는 이 서비스에 과하다. Postgres에 6~8GB 주면 데이터셋 전체가 메모리에 올라간다. 사실상 인메모리 속도로 돈다.

## 3. DB — VM 내부 PostgreSQL

### VM에 두는 이유

**쿼리 왕복이 곱해진다.** 이 서비스의 무거운 화면(잔디/통계/시즌)은 집계 쿼리를 한 화면에서 5~6개 날린다. 같은 머신이면 유닉스 소켓으로 0.1ms 수준. 외부 클라우드 DB면 매 쿼리 10~50ms가 붙고 쿼리 수만큼 곱해진다.

**데이터가 작다.** 관리형 무료 티어는 대개 0.5GB급이라 애초에 안 맞고, 유료는 월 20~30달러부터인데 지금 그럴 이유가 없다.

**남는 RAM을 쓸 수 있다.** 24GB를 놀리면서 외부 DB에 돈 내는 건 손해다.

**가용성 논리가 성립 안 한다.** VM이 하나라 DB만 살아있어도 앱이 죽으면 서비스는 다운이다. 분리해서 얻는 게 없다.

**되돌리기 쉽다.** 나중에 분리해야 하면 `pg_dump` 하나면 옮겨진다. 반대로 지금 관리형으로 시작하면 매달 나간 돈은 안 돌아온다.

### 조건

**백업이 반드시 VM 밖으로 나가야 한다.** 이 조건이 지켜지지 않으면 이 결정은 틀린 결정이 된다. → 11장

### MySQL이 아닌 이유

이 서비스는 아래 두 가지를 반드시 쓴다.

- **잔디**: 기록 없는 날까지 365칸을 채워야 함 → `generate_series`로 날짜를 만들고 LEFT JOIN
- **연승**: 윈도우 함수로 계산 (애플리케이션 루프보다 훨씬 빠름)

Postgres 쪽이 명백히 편하다.

### Autonomous Database를 안 쓰는 이유

Oracle Always Free로 20GB 2개를 준다. 같은 리전이라 레이턴시도 괜찮다. 하지만 **Oracle Database**라 ORM 생태계 지원이 나쁘고 방언도 다르다. 개인 프로젝트에서 이걸 배우는 시간이 아깝다.

## 4. 백엔드 — NestJS

Express 대신 Nest를 고른 이유 셋.

**1. 스케줄 작업이 반드시 필요하다.**
자정에 미완료 미션을 LOSE로 확정하는 정산, 시즌 종료 집계, 알림 발송. `@nestjs/schedule`로 바로 붙는다.

**2. 엔티티가 16개다.**
미션/기록/시즌/랭킹/팔로우가 Phase별로 계속 붙는다. Express로 시작하면 결국 자기만의 모듈 규칙을 발명하게 되는데, 혼자 하면 Nest가 이미 정해준 것보다 나을 가능성이 낮다.

**3. API 명세를 코드에서 뽑을 수 있다.**
`@nestjs/swagger`로 DTO에서 문서가 나온다. 명세를 손으로 쓰고 코드와 어긋나게 두는 것보다 낫다.

비용은 초반 보일러플레이트와 데코레이터 학습. 며칠이고, 위 셋은 프로젝트 내내 돌아온다.

## 5. 프론트 — Next.js (App Router)

> 초기에는 Vite + React SPA로 정했다가 Next.js로 변경했다. 아래에 변경 경위와 지켜야 할 조건을 남긴다.

### 왜 Next.js인가

**Phase 2 공개 프로필 때문이다.** 잔디와 전적을 링크로 공유하는 것이 이 서비스의 유입 경로다(35장). `/@닉네임` 페이지에 OG 미리보기와 SEO가 필요하고, SPA로는 그 시점에 별도 처리를 붙여야 한다.

라우팅·번들링·이미지 최적화가 기본으로 붙는 것도 혼자 하는 프로젝트에서 이득이다.

### 지켜야 할 조건 — 인증을 RSC로 끌어들이지 않는다

Next를 뺐던 원래 이유가 **인증 복잡도**였다. React Native가 오기 때문에 토큰 기반(access/refresh)으로 가야 하는데, RSC에서 쿠키를 들고 API 서버로 포워딩하는 구조는 혼자 관리하기 성가시다.

**그래서 이렇게 쓴다.**

- **인증이 필요한 화면은 RSC에서 fetch 하지 않는다.** 데이터는 브라우저에서 API를 호출한다
- Next는 **라우팅·번들링·공개 페이지 SSR**에만 쓴다
- 데이터 계층은 SPA와 동일하게 유지한다 → 나중에 React Native가 같은 API 클라이언트를 그대로 쓴다

이 조건이 깨지면 Next를 뺐던 이유가 그대로 돌아온다.

### 공개 프로필(Phase 2)만 SSR

`/@닉네임` 경로는 로그인이 필요 없으므로 RSC에서 서버 렌더해도 인증 문제가 없다. **SSR이 실제로 필요한 곳은 여기뿐이다.**

## 6. 저장소 구조 — 단일 레포 모노레포

```
apps/
  api        NestJS
  web        Next.js
  mobile     React Native (Phase 2 이후)
packages/
  core       승패 판정 · 달성률 · 연승 · 날짜 경계 (순수 함수)
  types      공유 타입 / API DTO
  api-client API 호출 래퍼
```

패키지 매니저: **pnpm workspaces**. Turborepo는 빌드가 느려지면 그때.

### 레포를 나누지 않는 결정적 이유 — `packages/core`

승패 판정, 달성률, 연승 계산을 **서버와 클라이언트가 같이 쓴다.** 체크하자마자 화면을 즉시 갱신하려면(낙관적 UI) 클라이언트에도 같은 로직이 필요하다.

레포를 나누면 이걸 공유하는 방법이 사설 npm 패키지 배포뿐이다.

```
core 수정 → 버전 올림 → 배포 → api 버전 올림 → web 버전 올림 → 각각 배포
```

혼자 하면서 매번 이걸 하면 결국 안 하게 되고, 양쪽에 로직을 복붙하게 된다. 그 순간 **서버가 판정한 승패와 화면에 뜬 승패가 어긋나는** 버그가 생긴다. 이 서비스에서 가장 치명적인 종류다.

한 레포면 파일만 고치면 끝난다.

**타입도 같은 이유.** API 응답 타입을 바꾸면 웹 빌드가 즉시 깨진다. 이건 장점이다. 레포가 나뉘면 안 깨지고 런타임에 터진다.

**멀티 레포의 장점(팀 분리, 릴리즈 주기 분리, 권한 분리)이 지금 하나도 해당 안 된다.**

**나중에 나누는 건 쉽다.** 하나 → 둘은 히스토리까지 살려 쪼갤 수 있다. 반대는 훨씬 귀찮다. 되돌리기 쉬운 쪽을 먼저 고른다.

### 프론트만 고쳐도 서버가 배포되는 문제

CI에서 경로 필터로 해결한다. `apps/api/**` 변경 시 API만, `apps/web/**` 변경 시 웹만.

## 7. ORM — Prisma + 집계는 raw SQL

```
CRUD (대부분)     → Prisma
집계 10여 개      → raw SQL, 한 폴더에 모아두고 반환 타입 명시
```

### 이유

쿼리 분포를 보면 **대부분이 단순 CRUD**다. 오늘의 미션 조회, 체크 처리, 미션 CRUD, 프로필 조회. Prisma가 제일 잘하는 영역이고, 스키마 파일 하나로 관리되는 것과 마이그레이션 안정성이 Phase 3까지 스키마가 계속 바뀔 이 프로젝트에서 크게 먹힌다.

집계는 잔디/통계/시즌/랭킹 정도로 다 합쳐도 10개 안쪽이다. **Prisma로 억지로 짜는 것보다 SQL로 쓰는 게 명확하다.** 윈도우 함수와 `generate_series`가 필요한 쿼리들이다.

### 알고 있어야 할 단점

raw SQL 구간은 **타입이 자동으로 안 나온다.** 반환 타입을 손으로 적어야 하고, 컬럼을 바꿔도 컴파일러가 안 잡아준다.
→ **그 10여 개 쿼리는 테스트로 덮는다.** (16장)

`apps/api/src/**/queries/` 처럼 한 곳에 모아둔다. 느려졌을 때 어디를 튜닝할지 한눈에 보인다.

### TypeORM을 안 쓰는 이유

Nest 공식 통합이라 후보에 오르지만 **마이그레이션이 불안정하기로 유명하다.** 스키마가 오래 굴러갈 프로젝트에서 제일 아픈 부분이다.

## 8. 인증

### 소셜 로그인만 — 구글 + 카카오

이메일/비밀번호를 안 받는다.

매일 여는 앱인데 가입 단계에서 이메일 인증하고 비밀번호를 정하게 하면 이탈이 크다. 비밀번호를 직접 다루면 해싱·재설정 메일·유출 대응까지 떠안는데 혼자 하는 프로젝트에서 얻는 게 없다.

**앱을 낼 때 애플 로그인을 추가해야 한다.** 선택이 아니라 의무다. iOS 앱에 다른 소셜 로그인이 있으면 애플 로그인도 제공해야 심사를 통과한다.

### 토큰

```
access   30분,  메모리에만
refresh  90일,  DB 저장 + 사용 시마다 회전
```

**JWT로 가는 이유**: RN이 온다. 세션 쿠키는 웹에선 편하지만 앱에서 다루기 나쁘다. 갈 곳이 정해져 있으니 처음부터 토큰으로 간다.

**refresh를 DB에 두는 이유**: 무효화가 가능해야 한다. 기기 분실이나 로그아웃 시 서버에서 끊을 수 있어야 하는데, JWT만 쓰면 만료 전까지 못 막는다.

**90일로 길게 잡는 이유**: 매일 열어야 하는 서비스인데 2주마다 로그아웃되면 그것 때문에 이탈한다. 회전까지 붙으면 매일 쓰는 사용자는 사실상 영구 로그인이다.

보관 위치
- 웹: refresh는 httpOnly 쿠키, access는 메모리
- 앱: refresh는 Keychain/Keystore(SecureStore), access는 메모리

### 회전 함정

네트워크가 끊기거나 요청이 동시에 나가면 **같은 refresh가 두 번 날아온다.** 이걸 탈취로 보고 끊으면 멀쩡한 사용자가 로그아웃된다.
→ **회전 직후 1분 정도는 이전 토큰도 받아준다.**

### 스키마에 반영해야 할 것

**1. 카카오는 이메일을 안 줄 수 있다.**
이메일 제공이 선택 동의라 거부하면 안 온다. **이메일을 식별 키로 쓰면 안 된다.** `provider + provider_user_id`로 식별한다. 이메일에 unique를 걸면 카카오 가입에서 터진다.

**2. 계정 분리 문제.**
같은 사람이 구글로도 카카오로도 가입하면 계정이 둘이 되고 전적이 갈라진다. 이메일로 자동 병합하는 건 카카오가 이메일을 안 줄 수 있어 신뢰 불가고 보안상으로도 위험하다.

**MVP는 provider별 별개 계정으로 두되, 테이블을 미리 나눈다.**

```
User          사람 (전적, 프로필이 붙음)
AuthProvider  로그인 수단 (provider, provider_user_id)
User : AuthProvider = 1 : N
```

처음엔 1:1로 쓰다가 나중에 "계정 연결" 기능을 붙일 때 행 하나만 추가하면 끝난다. User에 다 때려넣으면 마이그레이션이 아프다.

**3. 기기별 로그아웃**: refresh 토큰 테이블에 기기 정보를 같이 둔다.

### 타임존 — 지금 컬럼을 넣어둬야 한다

이 서비스의 핵심 질문이 **"이 사용자에게 오늘이 언제 끝나는가"**다. 자정에 미완료를 LOSE로 확정해야 하는데, 누구 기준 자정이냐가 문제다.

- 서버 저장은 전부 **UTC**
- User에 **`timezone`**
- User에 **`day_start_offset`** (하루 시작 시각, 기본 0시)

날짜 경계 계산은 전부 이 둘을 거치게 하고 `packages/core`에 함수로 뺀다.

**`day_start_offset`을 지금 넣어두는 게 핵심이다.** 새벽 2시까지 공부하는 사용자가 "오늘 다 했는데 왜 패배냐"고 하는 상황은 반드시 나온다. 나중에 넣으려면 이미 쌓인 기록의 날짜를 전부 재계산해야 한다. 컬럼만 두고 기능은 나중에 열어도 된다.

## 8.5 도메인

**`nadaena.com`** — 「나 대 나」.

등록처는 **Cloudflare Registrar**를 쓴다.
- 원가에 가깝게 판다 (마진을 붙이지 않음)
- DNS가 무료
- 백업과 이미지 저장에 R2를 쓰므로 **한 계정에서 도메인 · DNS · 스토리지가 함께 관리된다**

DNS는 VM의 공인 IP를 A 레코드로 가리키게 한다. Caddy가 인증서를 받으려면 **도메인이 먼저 VM을 가리키고 80/443이 열려 있어야 한다.** (Oracle은 보안 목록과 인스턴스 iptables 양쪽을 열어야 한다 — 18장)

## 9. 인프라 구성

```
                    인터넷
                      │
                    :443
                      │
              ┌───────▼───────┐
              │     Caddy     │  자동 HTTPS
              └───┬───────┬───┘
        /api/*    │       │   나머지
              ┌───▼───┐ ┌─▼──────────┐
              │ Nest  │ │ web (정적)  │
              └───┬───┘ └────────────┘
                  │
            ┌─────▼─────┐
            │ PostgreSQL │  데이터 볼륨
            └───────────┘

         Cloudflare R2 ← 백업 / 업로드 이미지
```

전부 Docker Compose 한 파일로 묶는다. **VM이 날아가도 새 인스턴스에서 `docker compose up` 한 번으로 복구된다.** Oracle 무료 인스턴스 회수 리스크에 대한 실질적 보험이다.

### Caddy를 Nginx 대신 쓰는 이유

**HTTPS 인증서를 자동으로 발급하고 갱신한다.** Nginx는 certbot을 붙이고 갱신 크론을 관리해야 하는데, 혼자 하는 프로젝트에서 **인증서 만료로 서비스가 죽는 게 흔한 사고**다. 몇 달 뒤엔 잊어버린다.

설정은 이 정도가 전부다.

```
nadaena.com {
    handle /api/* {
        reverse_proxy api:3000
    }
    handle {
        root * /srv/web
        try_files {path} /index.html
        file_server
    }
}
```

`try_files {path} /index.html`은 React SPA용이다. **이게 빠지면 `/기록` 같은 주소를 새로고침할 때 404가 난다.**

단점: Nginx가 사실상 표준이라 막혔을 때 나오는 자료가 훨씬 많다. 다만 이 규모에선 성능 차이는 무의미하다.

## 10. 배포

### ARM 문제와 그 해법

GitHub Actions 기본 러너는 x86이다. arm64 이미지를 QEMU로 빌드하면 몇 배로 느려진다.

**그런데 문제가 되는 건 절반뿐이다.**

- **웹은 아키텍처와 무관하다.** React 빌드 결과물은 그냥 JS/CSS다. x86에서 빌드해도 결과물이 같다.
- **API만 arm64가 필요하다.** Node 소스는 상관없지만 **Prisma가 아키텍처별 쿼리 엔진 바이너리를 받는다.** 네이티브 모듈도 마찬가지다. `install`을 arm64에서 해야 한다.

### 파이프라인

```
main 푸시
   │
   ├─ 웹:  Actions에서 빌드 → dist를 VM으로 전송 → Caddy가 서빙
   │
   └─ API: Actions가 VM에 SSH → VM에서 docker build (arm64 네이티브)
                              → 마이그레이션 → 컨테이너 교체
```

4코어 ARM이면 도커 빌드는 충분히 소화한다. 빌드 중 서비스가 조금 느려지지만 초기엔 문제되지 않는다. 빌드가 아파지면 그때 ARM 러너를 쓰거나 이미지를 미리 만든다.

**배포 스크립트 끝에 `docker image prune`을 넣는다.** 빌드 캐시가 200GB를 채우는 주범이다. 안 하면 몇 달 뒤 디스크가 차서 배포가 안 된다.

### 배포 순서

```
백업 → 마이그레이션 → 새 컨테이너 → 헬스체크 → 이전 컨테이너 종료
```

`prisma migrate deploy`는 **새 컨테이너를 띄우기 전에** 돌린다. 순서가 반대면 새 코드가 없는 컬럼을 찾다가 터진다.

**되돌릴 수 없는 변경은 자동 파이프라인에 태우지 않는다.** 컬럼 삭제, 타입 변경은 손으로 한다. 컬럼 추가 정도만 자동.

배포마다 몇 초 끊긴다. MVP는 그래도 된다. 무중단은 필요해지면.

### 시크릿

`.env`를 VM에 직접 두고 Compose가 읽는다. **GitHub Secrets에는 SSH 키만** 넣는다. DB 비밀번호는 GitHub에 올라가지 않는다.

`.env.example`은 커밋하고, Nest 부팅 시 Zod로 검증해서 **누락되면 즉시 죽게** 한다. 런타임 중간에 undefined로 터지는 것보다 낫다.

## 11. 백업

**VM에 DB를 둔 결정의 전제 조건이다.** 이게 없으면 3장의 결정은 틀린 결정이 된다.

### 백업을 Oracle에 두면 안 된다

VM DB의 진짜 위험은 **Oracle 무료 계정 정지 / 인스턴스 회수**다. 백업을 Oracle Object Storage에 두면 같은 계정이라 함께 날아간다. 위험을 하나도 안 줄인 것이 된다.

→ **다른 제공자에 둔다. Cloudflare R2** (무료 10GB). Backblaze B2도 가능.

### 구성

```
매일 새벽  pg_dump → gzip → R2 업로드
보관       일 7개 / 주 4개 / 월 6개
```

압축하면 초반엔 수십 MB다. 몇 년 쌓아도 무료 한도를 안 넘는다.

**업로드된 이미지도 백업 대상이다.** DB만 살리고 이미지가 없으면 프로필이 다 깨진다. (12장에서 R2에 두므로 자연히 해결)

### 이중화

| 수단 | 용도 |
| --- | --- |
| Oracle 블록 볼륨 자동 스냅샷 | VM은 살아있고 데이터만 깨졌을 때 빠른 복구 |
| R2의 pg_dump | 계정째 날아갔을 때 |

용도가 다르다. 둘 다 켠다.

### 복구를 한 번은 해봐야 한다

**한 번도 복구해본 적 없는 백업은 백업이 아니다.**

실제로 흔한 일: 매일 덤프는 잘 돌았는데 옵션이 잘못돼 스키마만 있고 데이터가 없거나, 압축이 깨져 있거나, 복구 명령을 몰라 헤매는 것.

→ **세팅 직후 로컬에서 실제로 복구해서 서비스가 뜨는지 확인하고 넘어간다.** 30분이면 된다.

---

## 12. 파일 저장 — Cloudflare R2

프로필 이미지를 VM 디스크가 아니라 R2에 둔다.

**이유**
- VM 디스크에 두면 백업 대상이 하나 늘고, 인스턴스 재생성 때 같이 옮겨야 한다
- 이미지 트래픽이 VM을 거치면 대역폭과 CPU를 쓴다
- **R2는 egress가 무료다.** 이미지 서빙에 이게 크다
- 백업으로 이미 R2를 쓰므로 계정을 하나 더 만들 필요가 없다

**업로드 방식**: API가 presigned URL을 발급하고 **클라이언트가 R2로 직접 업로드**한다. 이미지 바이트가 API 서버를 안 거친다.

**리사이즈는 클라이언트에서** 한다(256px 정도). 서버에 이미지 처리(sharp)를 안 넣는다 — ARM에서 빌드도 번거롭고 CPU도 아깝다.

**초기엔 업로드가 거의 필요 없다.** 소셜 로그인이 프로필 이미지 URL을 준다. 그걸 기본값으로 쓰면 되고, 직접 업로드는 원하는 사람만 한다.

## 14. 캐시 — MVP에서 제외

Redis를 넣지 않는다.

- 세션이 JWT라 세션 저장소가 필요 없다
- 24GB RAM에서 Postgres가 데이터셋을 통째로 캐싱한다
- 이 데이터 규모에서 캐시 계층은 복잡도만 늘린다

**Phase 2 랭킹 때 도입한다.** 랭킹은 Redis sorted set이 정확히 그 용도로 만들어진 자료구조라 그때가 진짜 필요한 시점이다.

## 15. 로그 · 모니터링

## 16. 개발 환경

### 로컬

- **Postgres는 도커로** 띄운다 (프로덕션과 같은 메이저 버전)
- API/웹은 로컬에서 직접 실행 (핫 리로드)
- `docker-compose.dev.yml`을 프로덕션용과 분리

### 린터 · 포매터 — Biome

ESLint + Prettier 조합은 모노레포에서 설정이 금방 지저분해진다. Biome은 린트와 포맷을 하나로 처리하고 설정이 짧고 빠르다.

리스크는 플러그인 생태계가 좁다는 것인데, 이 프로젝트는 특수한 룰이 필요 없다.
(Nest 기본 ESLint 세팅을 유지하고 싶으면 그것도 무방하다.)

### 테스트 — Vitest

**원칙: 승패 규칙은 전부 덮고, CRUD는 안 덮어도 된다.**

| 대상 | 범위 |
| --- | --- |
| `packages/core` | **필수, 촘촘하게.** 승패 판정 · 달성률 · 연승 · 날짜 경계 · 타임존 |
| 집계 raw SQL | **필수.** 타입이 안 잡아주는 구간이라 테스트가 유일한 안전망 |
| API | 주요 플로우 통합 테스트 (실제 Postgres 띄우고) |
| 웹 | 최소. E2E는 MVP 이후 |

`core`가 가장 중요하다. 서비스의 모든 숫자가 여기서 나오고, 서버와 클라이언트가 같이 쓴다.

### 브랜치 · 커밋

- `main` + feature 브랜치, PR로 머지 (혼자라도 diff를 한 번 보게 된다)
- Conventional Commits (`feat` / `fix` / `refactor` / `chore`)
- `main` 푸시 = 배포

## 18. 미리 알아둘 함정

나중에 하루씩 날릴 수 있는 것들. 겪을 때 "아 이거였구나" 하라고 모아둔다.

| 상황 | 내용 |
| --- | --- |
| **Oracle 포트가 안 열림** | 콘솔의 보안 목록(Security List)만 열어선 안 된다. **인스턴스 안쪽 iptables에도 규칙이 걸려 있다.** "보안 그룹 다 열었는데 왜 안 되지"로 반나절 날리는 게 Oracle에서 제일 흔하다 |
| **pnpm + React Native** | Metro 번들러가 pnpm의 심볼릭 링크 구조를 잘 못 씹는다. mobile만 `node-linker=hoisted`로 두거나 Metro의 `watchFolders`/`nodeModulesPaths`를 손봐야 한다 |
| **카카오 이메일 없음** | 이메일 제공이 선택 동의다. 이메일에 unique를 걸면 카카오 가입에서 터진다 |
| **SPA 새로고침 404** | Caddy에 `try_files {path} /index.html`이 없으면 `/기록` 새로고침 시 404 |
| **디스크 참** | 도커 빌드 캐시 · 로그 · WAL. DB가 아니라 이것들이 200GB를 채운다 |
| **refresh 회전 로그아웃** | 동시 요청으로 같은 토큰이 두 번 오면 정상 사용자가 끊긴다. 유예 시간 필요 |
| **인증서 만료** | Caddy를 쓰면 자동이지만, Nginx로 바꾸면 이게 다시 리스크가 된다 |
| **애플 로그인 의무** | iOS 앱에 다른 소셜 로그인이 있으면 애플 로그인 없이는 심사를 통과 못 한다 |
