## 3. 상태 정의

화면을 그리기 전에 상태를 먼저 못 박는다. 이 값이 그대로 타입이 된다.

### 미션 상태

```ts
type MissionResult = 'PENDING' | 'WIN' | 'LOSE';
```

| 상태 | 언제 |
| --- | --- |
| `PENDING` | 아직 체크 안 함 |
| `WIN` | 사용자가 체크 |
| `LOSE` | **자정에 자동 확정** |

> 진행 중에는 `LOSE`가 없다. 사용자가 스스로 패배를 선언하게 만들지 않는다.
> 원문 24장 화면에 `LOSE`가 보이는 것은 자정이 지난 뒤의 상태다.

### 일일 상태

```ts
type DailyResult = 'IN_PROGRESS' | 'WIN' | 'DRAW' | 'LOSE' | 'REST';
```

| 상태 | 조건 |
| --- | --- |
| `REST` | 그날 확정된 미션이 0개 |
| `IN_PROGRESS` | 자정 전, 아직 승리 미확정 |
| `WIN` | 달성률 50% 초과 |
| `DRAW` | 정확히 50% |
| `LOSE` | 50% 미만 |

### 승리는 자정 전에 확정된다

달성률의 분모는 **그날 전체 미션 수로 고정**이다. 따라서 완료 수만으로 결과가 결정된다.

```
미션 5개 · 3개 완료  →  3/5 = 60%  →  남은 2개를 못 해도 승리
```

**확정 조건**: `완료 수 > 전체 수 ÷ 2`

승리는 조기 확정되지만 **패배와 무승부는 자정까지 확정되지 않는다.** 남은 미션을 다 하면 결과가 바뀔 수 있기 때문이다.

> 좋은 소식만 일찍 알린다. 2장의 "실패로 의욕이 꺾이는 구조"를 만들지 않는다.

## 4. S3 — 오늘 (가장 중요한 화면)

앱/웹 진입 시 기본 화면.

### 4.1 진행 중

```
┌──────────────────────────────────┬───────────────────────┐
│ 2026.08.26 (수)                  │ 통산                   │
│                                  │ 127전 94승 5무 28패    │
│ 오늘의 승부          진행 중      │ 승률 74.0%             │
│                                  │ ─────────────────     │
│ ████████████░░░░░░░░  3/5  60%   │ 🔥 현재 7연승          │
│                                  │ 최장 12연승            │
│ ┌──────────────────────────────┐ │ ─────────────────     │
│ │ ✓  영어 공부       30분      │ │ 8월                    │
│ │ ✓  헬스            1시간 30분│ │ 21전 16승 5패          │
│ │ ✓  독서            30분      │ │ 승률 76.2%             │
│ │ ○  알고리즘        2문제     │ │ ─────────────────     │
│ │ ○  프로그래밍 공부  1시간    │ │ 이번 달                │
│ └──────────────────────────────┘ │ ▪▪▫▪▪▪▫▪▪▪▫▪▪...     │
│                                  │                       │
│ 한 줄 회고                        │                       │
│ ┌──────────────────────────────┐ │                       │
│ │                              │ │                       │
│ └──────────────────────────────┘ │                       │
└──────────────────────────────────┴───────────────────────┘
```

**완료한 미션을 위로 올린다.** 남은 것이 아래에 모여서 "무엇을 더 해야 하는가"가 바로 보인다.

**진행 바에 절대 개수(`3/5`)를 함께 표시한다.** 퍼센트만 있으면 "몇 개 더 하면 이기는가"를 계산해야 한다.

### 4.2 승리 확정 (자정 전)

3개를 완료하는 순간.

```
│ 오늘의 승부          🏆 WIN                              │
│                                                         │
│ ████████████░░░░░░░░  3/5  60%                          │
│ 오늘 승리했습니다. 남은 2개는 더 해도 좋습니다.            │
```

**남은 미션을 계속 체크할 수 있다.** 달성률은 계속 올라가고 잔디가 진해진다.
승리한 뒤에도 할 이유가 남아 있어야 한다.

### 4.3 종료 — 승 / 무 / 패

자정이 지나면 미완료가 `LOSE`로 확정된다. (다음 날 진입 시 어제 결과로 확인)

```
│ 오늘의 승부          🏆 WIN     4/5  80%                 │
│ 오늘의 승부          ⚖ DRAW     2/4  50%                 │
│ 오늘의 승부          ● LOSE     1/5  20%                 │
```

**패배 화면에 위로 문구를 넣지 않는다.** "괜찮아요" 같은 문구는 패배를 사건으로 만든다.
대신 **누적 전적을 옆에 그대로 둔다.** `127전 94승` 옆에 오늘의 1패가 있는 것이 문구보다 낫다. (2장 · 35장)

### 4.4 쉬는 날

그날 확정된 미션이 0개.

```
│ 2026.08.30 (일)                                          │
│                                                          │
│ 오늘은 쉬는 날입니다                                      │
│ 예정된 미션이 없습니다. 연승은 유지됩니다. (🔥 7연승)      │
│                                                          │
│ [ 오늘 미션 추가하기 ]                                    │
```

**연승이 유지된다는 것을 명시한다.** 이게 안 보이면 사용자는 쉬는 날에 불안해진다.

미션 추가는 당일에도 허용되므로(6.5) 버튼을 남겨둔다.

### 4.5 미션 없음 (가입 직후 / 전부 비활성)

```
│ 아직 승부가 없습니다                                      │
│ 매일 할 일을 정하면 오늘부터 기록이 시작됩니다.            │
│                                                          │
│ [ 첫 미션 만들기 ]                                        │
```

쉬는 날과 **다른 화면이다.** 쉬는 날은 "오늘은 없음", 이건 "아직 시작 안 함"이다.

### 4.6 어제 기록 유도

7일 이내 수정이 가능하므로(6.7), 어제 미완료가 있으면 오늘 화면 상단에 한 줄 띄운다.

```
│ 어제 체크하지 않은 미션이 있습니다.  [ 확인 ]  (D-6)      │
```

`(D-6)` = 수정 가능 기한. **남은 기간을 같이 보여준다.** 없으면 언제까지 가능한지 알 수 없다.

> 이 유도가 없으면 7일 규칙이 사실상 죽는다. 사용자는 기록 화면에 잘 안 들어간다.

### 4.7 한 줄 회고

- **언제든 쓸 수 있다.** 하루가 끝나야 쓸 수 있게 하면 대부분 안 쓴다
- 하루에 하나. 수정 가능
- 수정 기한은 기록 수정과 동일하게 **7일**

## 5. S4 — 기록 · 캘린더

상단 서브 메뉴: `캘린더 / 통계`

**잔디를 별도 탭으로 두지 않는다.** 연간 잔디는 이 화면의 **년 뷰**가 담당한다.
같은 것을 두 군데서 보게 하면 사용자는 매번 "어디로 가야 하지"를 판단해야 한다.

### 5.1 뷰 전환 — 일 / 주 / 월 / 년

하나의 캘린더에서 범위만 바꾼다. **계획용 달력과 조회용 달력을 나누지 않는다.**

| 뷰 | 내용 |
| --- | --- |
| 일 | 그날 하나. 과거는 전적·달성률, 미래는 예정 미션 + `이 날 미션 추가` |
| 주 | 7일 목록. **미션 이름이 그대로 보인다** — 계획 확인에 가장 유용 |
| 월 | 그리드. 과거는 결과 색 막대, 미래는 예정 개수만큼 점 |
| 년 | **연간 잔디** |

`‹ ›` 는 현재 뷰 단위로 움직인다 (하루 / 일주일 / 한 달 / 일 년).

### 5.2 시점에 따라 다르게 보인다

| 시점 | 표시 | 클릭 |
| --- | --- | --- |
| 과거 | 승/무/패 색 | 전적 · 달성률 · **수정 가능 기한(D-N)** |
| 오늘 | 강조 테두리 | 진행 상황 |
| 미래 | 예정 미션 개수 | 예정 목록 + `이 날 미션 추가` |

미래 날짜의 예정 미션은 `packages/core` 의 `occursOn` 으로 계산한다. 저장하지 않는다.

### 5.3 월 뷰는 항상 6주를 그린다

달마다 4~6주로 칸 수가 달라지면 **월을 넘길 때마다 화면 높이가 출렁인다.**
앞뒤 달의 날짜를 흐리게 채워 항상 42칸을 유지한다.

### 5.4 달력에서 미션을 추가할 때

미래 날짜의 `이 날 미션 추가` 로 들어오면 **기본 반복이 `반복 안함`** 이다.

날짜를 골라서 들어온 사람은 그날 하루를 생각하고 있다.
미션 목록에서 `+ 추가` 로 들어오면 기본이 `매일` 이다. **들어온 경로가 다르면 기대도 다르다.**


**6.5 규칙을 사용자에게 반드시 설명해야 한다.** 지우고 오늘 화면에 그대로 있으면 버그로 보인다.

"지난 기록은 그대로 남는다"도 같이 알린다. 전적이 사라질까 봐 삭제를 못 하는 상황을 막는다.

### 첫 미션은 1~3개로 유도한다

37장 원칙(사용자가 시스템을 위해 살지 않도록)과 직결된다.

**미션이 많을수록 승리가 어려워진다.** 50% 초과가 승리 조건이므로 미션 8개면 5개를 해야 이긴다. 첫날부터 지면 그대로 이탈한다.

```
│  처음에는 2~3개로 시작하는 것을 권합니다.  │
│  미션이 많을수록 승리 조건도 올라갑니다.   │
```

**막지는 않는다.** 권유만 한다.

### 추천 미션 (기본 제공)

루틴 공유(20장)는 Phase 3라 MVP에는 공유된 루틴이 없다. **서비스가 기본 목록을 제공한다.**

```
운동 30분 · 독서 30분 · 영어 공부 30분 · 알고리즘 1문제 · 일찍 일어나기
```

## 14. 이 문서에서 결정한 것

기획서에 없어서 화면을 그리며 정한 것들. 되돌릴 수 있다.

| # | 결정 | 이유 |
| --- | --- | --- |
| 1 | 진행 중에는 `LOSE`를 표시하지 않는다 | 스스로 패배를 선언하게 만들지 않는다 |
| 2 | **승리는 자정 전에 확정된다** | 분모가 고정이라 수학적으로 결정된다. 좋은 소식은 일찍 알린다 |
| 3 | 승리 후에도 남은 미션을 체크할 수 있다 | 잔디 농도가 올라간다. 이긴 뒤에도 할 이유가 남는다 |
| 4 | 완료한 미션을 목록 위로 올린다 | 남은 것이 아래에 모인다 |
| 5 | 패배 화면에 위로 문구를 넣지 않는다 | 문구가 패배를 사건으로 만든다. 누적 전적이 더 낫다 |
| 6 | 오늘 화면에 어제 미체크 유도를 띄운다 | 없으면 7일 수정 규칙이 사실상 죽는다 |
| 7 | 회고는 하루 중 언제든 쓸 수 있다 | 하루가 끝나야 쓰게 하면 대부분 안 쓴다 |
| 8 | 미션 삭제 시 6.5 규칙을 안내한다 | 안 하면 버그로 보인다 |
| 9 | 미션 생성 화면에 "난이도는 승패에 영향 없음"을 적는다 | 오해를 미리 막는다 |
| 10 | 온보딩에서 첫 미션 1~3개를 권유한다 (막지 않음) | 미션이 많을수록 승리 조건이 올라간다 (R-4) |
| 11 | MVP 추천 미션 목록을 서비스가 제공한다 | 루틴 공유가 Phase 3라 공유된 루틴이 없다 (R-4) |
| 12 | **캘린더를 하나로 합친다** (과거 조회 + 미래 계획) | 달력이 둘이면 매번 "어디로 가야 하지"를 판단해야 한다 |
| 13 | **잔디 탭을 없애고 캘린더 년 뷰로 흡수** | 같은 것을 두 군데서 보게 하지 않는다 |
| 14 | 월 뷰는 항상 6주(42칸) | 달마다 높이가 바뀌면 화면이 출렁인다 |
| 15 | 달력에서 추가하면 기본 반복이 `반복 안함` | 날짜를 골라 들어온 사람은 그날 하루를 생각한다 |
| 16 | 반복 첫 항목은 `반복 안함` | 반복은 필수가 아니다. 구글 캘린더와 같은 순서 |
| 19 | 랜딩을 `/`, 앱을 `/today` 로 | 로그인 화면이 첫 화면이면 서비스를 모르고 로그인을 요구받는다 |
| 20 | **피드 대신 둘러보기** | 초기엔 피드가 텅 빈다. 빈 피드는 이탈을 늘린다 |
| 21 | 온보딩에서 **필요 승수를 숫자로** 보여준다 | "3개 중 2개를 해내면 승리" — 과욕을 숫자로 막는다 |
| 22 | 잔디 툴팁을 CSS 로만 만든다 | 서버 컴포넌트(랜딩)에서도 쓰고, 기본 `title` 은 1초 지연이 있다 |
| 17 | 어제 유도 배너에 **실제 날짜**를 쓴다 | 최근 7일 중 패배가 있는 날이라 어제가 아닐 수 있다 |
| 18 | 남은 기한(D-N)을 **앱이 아는 오늘**로 센다 | 기기 시계를 쓰면 서버 판단과 어긋난다 (07-api.md 8장) |

## 14.5 S0 — 랜딩 · 둘러보기

로그인 화면을 첫 화면으로 두면, 서비스가 뭔지도 모르고 로그인을 요구받는다.

### 왜 피드가 아닌가

초기에는 사용자가 거의 없어 **피드가 텅 빈다.** 빈 피드는 "아무도 안 쓰는 서비스"라는 신호를 줘서 이탈을 오히려 늘린다. 피드는 Phase 3이고, 팔로우(Phase 2) 없이는 "누구 걸 보여줄지"도 정의되지 않는다.

### 랜딩은 그림으로 설명한다

이 서비스의 매력은 문장이 아니라 **채워진 잔디와 전적**이다.
랜딩은 데모 계정의 **실제 1년치 잔디**를 서버 렌더로 보여준다. 정적 이미지가 아니라 앱에서 쓰는 것과 같은 컴포넌트다.

로그인이 필요 없어 SSR 이 가능하고, 검색엔진과 링크 미리보기에 잡힌다.

### 둘러보기 — `/demo`

오늘 화면과 통계를 **읽기 전용**으로 보여준다. 체크는 눌러도 반응하지 않는다.
상단에 `다른 사람의 기록입니다` 배너를 고정해 자기 기록으로 착각하지 않게 한다.

### 데모 계정

`users.isDemo` 로 표시한 계정 하나만 공개된다.
조건을 계정 속성으로 두면 **실제 사용자 데이터가 실수로 공개될 여지가 없다.**
